# M5 설계 — 클릭 도망·회복·애니메이션 (F-09 ~ F-13)

작성일: 2026-09-21 · 상태: 사용자 위임, 결정은 이 문서에 기록

## 왜 이것이 다음인가

M1~M4c는 **물고기가 스스로 움직이는 세계**를 만들었다. 아이가 할 수 있는 일은 방향키로 자기
물고기를 모는 것뿐이고, 화면의 나머지 36마리는 아이가 무엇을 하든 반응하지 않는다. M5는 이
게임에서 **아이가 세계를 건드릴 수 있는 유일한 수단**을 붙인다. 클릭 한 번에 물고기 한 마리가
놀라서 달아나고, 2초 뒤 아무 일 없었다는 듯 돌아온다. F-09~F-13이 전부 그 한 동작의 서로 다른
면이다.

- **F-09** 무엇을 눌렀는지 — 가장 앞의 한 마리, 빈 바다는 아무것도.
- **F-10** 어느 쪽으로 — 클릭 지점에서 멀어지는 방향, 퇴화 입력의 폴백까지.
- **F-11** 얼마나 오래 — 0.8초 도망 → 1.2초 회복, 재입력 규칙.
- **F-12** 누구에게 — 배경 물고기는 자동 유영 복귀, 내 물고기는 방향키와의 우선순위.
- **F-13** 어떻게 보이는가 — 회전·꼬리 진폭·유영 주기가 속도와 상태를 따르고, 순간 반전도
  미끄러짐도 없다.

**F-13은 M5의 부록이 아니라 M5가 만드는 결함의 검사다.** 이 프로젝트에서 물고기의 원하는 방향이
한 프레임에 최대 180도 뒤집히는 순간은 지금까지 **벽에서 속도가 0을 통과할 때** 하나뿐이었다.
도망은 두 번째이자 더 거친 경우다 — 정면을 헤엄쳐 오던 물고기의 코앞을 클릭하면 원하는 방향이
그 자리에서 반대가 된다. M3에서 한 번, M4c에서 또 한 번 이 프로젝트를 물었던 종류의 결함이
정확히 여기서 다시 나올 수 있다.

## 현재 상태 확인 — `docs/TASK.md`의 기록은 관대하다

`docs/TASK.md`는 "미구현 Unreal 연동: F-09 레이캐스트(M5)"라고만 적어 두었다. 코드를 직접 확인한
결과는 다르다.

```
$ grep -rn "Flee\|flee" unreal/Aquarium/Source/   # → 0건
```

- `rules/include/aquarium/Flee.h`와 `tests/test_flee.cpp`(6개 테스트)는 규칙 계층 마일스톤에서
  이미 만들어졌고 지금도 통과한다.
- 그러나 **Unreal 쪽에는 도망이 한 글자도 없다.** `AFishActor`에 `FleeStateMachine` 멤버가 없고,
  `Touch()`를 부르는 곳도, `State()`를 읽는 곳도 없다. 마우스 버튼은 어디에도 바인딩되어 있지 않다.
- 즉 미구현인 것은 **F-09의 적중 판정뿐이 아니라 F-09~F-13의 엔진 연동 전부**다. 규칙 계층이
  이미 덮고 있는 것은 F-10·F-11·F-12의 *순수 로직*이고, 그것을 실제로 구동하는 코드가 없다.

이 문서는 그 차이를 전제로 쓴다.

### `Flee.h`가 이미 보장하는 것 / 보장하지 않는 것

| 항목 | 상태 |
|---|---|
| 클릭 지점에서 멀어지는 방향 (F-10) | **있음** — `ComputeFleeDirection` |

| 0.8초 → 1.2초 → 정상 상태 전이 (F-11) | **있음** — `Step(dt)`가 한 스텝이 두 구간을 넘어가는 경우까지 처리 |
| 도망 중 재입력 무시, 회복 중 재입력은 도망 재시작 (F-11) | **있음** — `Touch()` 첫 줄 |
| 도망 중 플레이어 입력 억제, 회복부터 복원 (F-12) | **있음** — `EffectiveInput()` |
| **가속** (F-10의 "회전·**가속**") | **없음** — 방향만 준다. 속도 배율이라는 개념 자체가 없다 |
| **퇴화 입력에서의 비영 벡터 보장** | **없음** — 위 표의 3행. 엔진이 0을 받으면 `StepMotion`이 감속으로 해석해 "놀랐는데 멈추는" 물고기가 된다 |
| **어느 물고기를 건드렸는가** (F-09) | **없음** — 적중 판정 개념이 없다 |
| 배경 물고기의 자동 유영 복귀 (F-12) | **없음** — `EffectiveInput`은 플레이어 입력용이다. 배경 물고기의 Wander 방향에 같은 우선순위를 적용하는 것은 엔진 쪽 규칙 순서 문제 |
| 애니메이션 (F-13) | **무관** — `SwimAnimation`·`Facing`이 이미 담당 |

따라서 **규칙 계층에서 늘릴 것은 정확히 세 가지**다: (1) 비영 벡터 보장, (2) 속도 배율,
(3) 적중 판정. 나머지는 엔진 연동이다.

## 결정 사항 (아쿠부장 판단, 2026-09-21)

| 항목 | 결정 | 이유 |
|---|---|---|
| 도망 로직의 위치 | **`Flee.h`를 재사용하고 엔진에 다시 쓰지 않는다.** 부족한 것(비영 보장·속도 배율·적중 판정)은 전부 `Flee.h`에 Catch2 테스트와 함께 **확장**한다 | 이 프로젝트의 모든 행동(`Steering`·`Wander`·`Bounds`·`Boids`·`Obstacles`·`Facing`)이 순수 함수이고 엔진은 그것을 구동할 뿐이다. 엔진 안에 상태 기계를 넣으면 0.8초/1.2초 경계와 반복 클릭 전이를 검증할 방법이 캡처를 눈으로 보는 것밖에 남지 않는다. 같은 규칙을 두 군데 두는 것은 M4b의 프롭 레인 사고 그대로다 |
| **적중 판정 방식 (F-09)** | **엔진 역투영 1회 + 규칙 계층의 해석적 광선–평면 판정.** 클릭한 화면 좌표를 `APlayerController::DeprojectScreenPositionToWorld`로 **월드 광선 하나**로 바꾼 다음(투영 수학은 엔진 것을 쓴다 — 베끼지 않는다), 그 광선을 `aquarium::PickFrontmostHit`에 넘긴다. 물고기는 전부 X가 고정된 YZ 평면 위에 있으므로 물고기마다 나눗셈 한 번으로 **정확한** 교차점이 나오고, 평면 안에서 타원 하나로 적중을 판정한 뒤 **X가 가장 작은 것 하나**를 고른다. 라인 트레이스는 쓰지 않는다 | **라인 트레이스가 틀리는 이유가 구체적으로 있다.** FBX 임포트가 자동 생성한 물리 애셋의 본별 캡슐은 몸보다 훨씬 뚱뚱하다 — M4a에서 블루탱의 물리 AABB가 43.9 × 26.0 cm였고 실제 메시는 25.0 × 3.6 cm였다(`FishActor.cpp`의 `bComponentUseFixedSkelBounds` 주석). 그 캡슐로 트레이스하면 빈 물을 눌러도 적중하고, 특히 **"가장 앞"의 판정이 틀린다**(뚱뚱한 앞쪽 캡슐이 뒤쪽 물고기의 몸을 가린다). 게다가 `SK_*_PhysicsAsset`은 M4a 후속 항목에 "미사용"으로 적혀 있는, 아무도 검증하지 않은 데이터다. 반대로 해석적 판정은 **화면에 실제로 그려지는 바운드에서 파생**되고, 평면 X가 고정이라는 사실을 쓰는 `Obstacles.h`의 방식과 같은 관용구이며, 비용은 클릭당 물고기 37마리 × (나눗셈 1 + 곱셈 몇 개)로 **매 프레임이 아니라 클릭당 한 번**이다 |
| 적중 도형 | **평면 안의 타원**(반폭 = 바운드 Y 반경, 반높이 = 바운드 Z 반경), 바운드는 `Body->CalcBounds(월드 트랜스폼)`에서 **파생** | 물고기는 옆에서 보면 길쭉한 타원이다. 원 하나로 하면 반폭 기준일 때 위아래가 과하게 잡히고 반높이 기준이면 꼬리 쪽이 안 잡힌다(M4c에서 산호를 원판 하나로 근사할 수 없던 것과 같은 이유). 반경을 C++ 상수표로 베끼지 않는 것은 M4b의 프롭 반경 사고 때문이다. 플레이어 물고기의 34 cm 정규화 스케일도 월드 트랜스폼을 쓰면 자동으로 반영된다 |
| 규칙 순서에서 도망의 자리 | **입력/Wander → 도망 → 무리 → 장애물 → 경계 → StepMotion → Clamp.** 도망은 *원하는 방향*을 **교체**하므로 입력/Wander와 같은 층이다. 단 **도망 중에는 무리(보이즈)를 건너뛴다** | 도망은 "어디로 가고 싶은가"의 답이지 그 답을 휘는 보정이 아니다. 그래서 입력/Wander 바로 다음이다. 뒤의 세 단계는 그대로 남겨야 한다 — 놀란 물고기가 바위를 뚫거나(M4c 보장) **화면 밖으로 나가면(F-07: "도망 중 경계" 검증 항목이 SRS에 명시되어 있다)** 안 되기 때문이다. **경계가 마지막에 이기는 M3의 보장은 손대지 않는다.** 반대로 무리는 건너뛴다: 응집이 도망을 자기 무리 쪽으로 도로 끌어당기면 "놀라서 달아났는데 제자리"가 되어 아이가 클릭의 결과를 읽을 수 없다. 분리까지 같이 꺼지지만, 도망은 0.8초이고 그 사이 관통이 생기면 장애물·경계가 아니라 **분리 복귀 시점**에 해소된다 |
| 가속 (F-10) | **`FleeParams::fleeSpeedScale = 2.2`** 를 추가하고 `FleeStateMachine::SpeedScale()`이 도망 중 2.2, 회복 중 2.2 → 1.0 선형 복귀, 정상 1.0을 돌려준다. 엔진은 그 값을 그 스텝의 `MotionParams::maxSpeed`에 곱한다 | F-10은 "회전·**가속**한다"이다. 방향만 바꾸면 배경 물고기는 40 cm/s로 유유히 방향만 트는 것으로 보이고 "놀랐다"가 읽히지 않는다. 회복 구간에서 한 번에 원래 속도로 떨어뜨리면 그 순간이 브레이크로 보이므로 선형 복귀로 한다. `accel`은 건드리지 않는다 — 가속도를 같이 올리면 첫 프레임에 속도가 튀어 F-13의 "미끄러짐"이 생긴다 |
| 폴백의 마지막 단 | `ComputeFleeDirection`이 **절대 0 벡터를 돌려주지 않게** 한다(최종 폴백 `{1, 0}`). 엔진이 넘기는 `fallbackDir`은 **평면 중심 방향**(`-Motion.position`의 정규화) | SRS F-10의 "정지 상태면 화면 중심 쪽의 유효 방향". 유영 평면은 평면 원점을 중심으로 대칭이고 그 원점은 카메라 축 근처이므로 평면 중심 방향이 곧 화면 중심 방향이다. 그런데 **물고기가 정확히 평면 중심에 정지한 채 자기 중심을 클릭당하면 세 폴백이 전부 0**이다. 지금 코드는 그때 0을 돌려주고, 엔진은 그것을 "입력 없음"으로 읽어 감속한다 — 즉 **놀라서 멈춘다.** 확률은 낮지만 아이가 자기 물고기를 멈춰 세우고 클릭하는 것은 가장 흔한 조작 중 하나다 |
| 입력 경로 | **`InputComponent->BindKey(EKeys::LeftMouseButton, IE_Pressed, ...)`.** Enhanced Input을 쓰지 않는다. `EKeys::LeftMouseButton`의 **더블클릭 이벤트(`IE_DoubleClick`)는 바인딩하지 않는다** | M3이 확인한 사실 그대로다 — 이 프로젝트의 Enhanced Input 기본값 때문에 레거시 ActionMapping은 무시되고, `BindKey`는 애셋 없이 동작하며 이미 Esc·방향키 8개로 증명되어 있다. Enhanced Input 애셋은 에디터 Python 경로로 재현할 수 없고, **재현 가능성이 이 프로젝트의 제1원칙**이다. 더블클릭을 바인딩하지 않는 이유는 따로 있다: macOS는 빠른 두 번째 클릭에 `IE_Pressed`와 `IE_DoubleClick`을 **둘 다** 보내므로, 둘 다 바인딩하면 아이가 연타할 때 한 번의 물리적 클릭이 두 번 처리된다 |
| 실제 클릭과 스크립트 클릭의 경로 | **한 함수(`HandleClickAt(FVector2D ViewportPos)`)로 합친다.** 실제 마우스는 `HandleClick()`이 커서 위치를 읽어 넘기고, 개발 전용 `-AquariumAutoClick`은 같은 함수에 좌표를 넘긴다 | 캡처 경로와 실제 경로가 다르면 캡처는 캡처만 검증한다. M4b의 프롭 레인 규칙이 두 군데 있어서 검증이 결함을 한 번도 못 잡은 것과 같은 구조다 |
| 헤드리스 검증 수단 | 개발 전용 플래그 **세 개**: `-AquariumAutoClick=<패턴>`(예약 클릭), `-AquariumClickLog=<csv>`(클릭별 결과 기록), `-AquariumNoFlee`(성능 항목 분해). 문법은 아래에 정확히 못 박는다 | 클릭은 시간 축의 사건이라 스틸로도 로그 한 줄로도 확인할 수 없다. **무엇을 눌렀고 무엇이 맞았는지**를 기계가 읽을 수 있는 형태로 남기지 않으면, "클릭이 하나도 발사되지 않았는데 그럴듯한 클립이 나오는" M4c의 사고가 그대로 재현된다 |
| 판정 산출물 | **클립이 1차, 스틸은 보조.** 같은 맵·같은 시드·같은 카메라·같은 자동 입력·같은 t | 도망은 전적으로 **움직임**이다. 정지 화면에서는 도망 중인 물고기와 그냥 헤엄치는 물고기를 구분할 수 없다. M4c와 같은 규약 |

## F-09 적중 판정 — 수치로 본 근거

카메라는 `(0, 0, 130)`에서 피치 −4°로 +X를 보고, 수평 FOV 75°다(`Scripts/build_reef_m1.py`의
`CAM_LOC`/`CAM_ROT`/`CAM_FOV`). 배경 물고기 평면은 X = 330~700의 36장, 플레이어 평면은 X = 220.

카메라가 축에 정렬되어 있지 않으므로(피치 −4°) **화면 좌표 → 평면 좌표를 직접 닫힌 식으로 쓰는
것은 엔진의 투영 수학을 베끼는 일**이고, 화면 비율·FOV·근평면을 어딘가에 또 적는 순간 M4b의
중복 규칙 사고가 된다. 그래서 역투영은 엔진에 맡기고(클릭당 1회), 그 결과인 **월드 광선**만
규칙 계층으로 넘긴다. 광선–평면 교차는 카메라가 어떻게 생겼든 무관하게 성립한다.

```
t = (depth - origin.x) / dir.x            // dir.x > 1e-4 가 아니면 적중 없음
hit = origin + dir * t                    // t > 0 이 아니면 그 평면은 뒤에 있다
u = (hit.y - center.x) / halfWidth
v = (hit.z - center.y) / halfHeight
적중 ⟺ u*u + v*v <= 1
```

`center`는 `BoidNeighbor::position`과 **같은 공유 프레임 `(worldY, worldZ)`** 을 쓴다. M4c가 이미
정한 좌표계를 그대로 쓰므로 새 좌표계를 하나 더 만들지 않는다. 가장 앞은 `depth`(= 평면 X)가
최소인 적중이다 — 카메라가 +X를 보므로 평면 X의 순서가 곧 화면 깊이 순서이고, 이 게임에서 평면
X는 물고기의 일생 동안 상수다.

**비용.** 클릭당 37회 반복, 반복당 나눗셈 1 + 곱셈 6 + 비교 2 ≈ 400 flop. 클릭 한 번의 총비용은
마이크로초 이하다. **매 프레임에 드는 비용은 0**이다 — 화면 좌표 계산을 틱마다 하지 않는 것이
이 설계의 핵심이다(37마리 화면 투영을 매 틱 돌리는 쪽은 프레임 여유가 5.4 %뿐인 지금 상황에서
근거 없이 쓸 수 있는 예산이 아니다). 틱마다 추가되는 것은 물고기당 `FleeStateMachine::Step`
하나 — 비교 두 번과 뺄셈 한 번이다.

## F-11 — 아이가 마우스를 연타하면 무슨 일이 일어나는가

물고기마다 자기 `FleeStateMachine`을 가지므로 상태는 물고기 단위다.

| 상황 | 결과 |
|---|---|
| 같은 물고기를 0.8초 안에 다시 클릭 | **무시.** 방향도 타이머도 그대로 (`Touch()` 첫 줄) |
| 같은 물고기를 회복 중(0.8~2.0초)에 클릭 | **도망 재시작.** 새 클릭 지점 기준으로 방향을 다시 계산하고 타이머를 0.8초로 되돌린다 |
| 다른 물고기를 연달아 클릭 | 각자 독립적으로 도망한다. 동시에 37마리 전부가 도망 상태일 수 있고 그래도 정상이다 — 상태는 물고기당 float 2개이고 비용은 유계다 |
| 한 번의 클릭이 여러 마리에 걸침 | **가장 앞 한 마리만.** `PickFrontmostHit`가 인덱스 하나를 돌려준다 |
| 빈 바다 클릭 | **아무 일도 없다.** 인덱스 −1이고 `Touch()`는 호출되지 않는다. 어떤 물고기의 상태도 바뀌지 않는다 |
| 내 물고기를 방향키를 누른 채 클릭 | 0.8초 동안 방향키는 무시되고 도망이 이긴다. 회복 시작 시점부터 **그 순간 실제로 눌려 있는** 방향키가 다시 적용된다 — 컨트롤러가 매 틱 `SetInputDirection`을 쓰므로 "클릭 당시의 낡은 입력"이 되살아나는 일은 구조적으로 없다. 아이가 도망 중에 키를 놓았으면 회복 시점에 그냥 감속한다 |
| 입장 화면에서 클릭 | 무시한다(`HasActiveSession()` 가드). 별명 입력칸·입장 버튼 클릭이 뒤쪽 물고기를 놀라게 하지 않는다 |
| HUD 나가기 버튼 클릭 | 무시한다(버튼 호버 가드). **이 가드만은 헤드리스로 검증할 수 없고 클립으로 확인한다**(아래 검증 표에 그렇게 적었다) |

아이가 초당 10회로 한 마리를 연타해도 상태 전이는 0.8초에 한 번씩만 일어난다. 즉 **`Flee.h`의
"도망 중 무시" 규칙이 곧 디바운스**이고, 따로 연타 방지를 넣지 않는다.

## F-12 — 내 물고기에서 아이가 실제로 겪는 것

내 물고기는 화면에서 가장 큰 물고기이고 아이가 계속 보고 있는 대상이다. 여기서 나올 수 있는
나쁜 경험은 두 가지고, 둘 다 설계로 막는다.

1. **"내 물고기가 말을 안 들어요."** 0.8초는 짧지만 조종 불능 구간인 것은 맞다. 그래서
   **경계 규칙은 도망 중에도 그대로 적용한다** — 도망이 화면 밖으로 끌고 나갈 수 없다. 또한
   회복 구간(1.2초)에서는 **방향키가 즉시 돌아온다.** 즉 아이가 조종할 수 없는 시간은 최대
   0.8초이고, 그 뒤 1.2초는 "조종은 되는데 아직 좀 빠른" 구간이다.
2. **"클릭했더니 물고기가 멈췄어요."** 위 결정표의 폴백 마지막 단이 이것을 막는다. 정지 상태로
   자기 중심을 클릭당한 물고기는 `{1, 0}`(화면 오른쪽)으로 도망한다. 멈추는 것보다 낫다.

**배경 물고기의 복귀**는 더 단순하다. 도망이 끝나면 `Desired`가 다시 `Wander->DesiredDirection`이
된다. `StepSwim`은 플레이어 조종 중에도 `Wander->Update()`를 계속 돌리고 있으므로(M3에서 넣은
것) 도망 2초가 지난 뒤 낡은 목표로 돌아가는 일이 없다 — **이 동작은 이미 있고 M5는 그것을
그대로 쓴다.**

## F-13 — 기존 테스트가 이미 덮는 것과, 그래도 필요한 것

이미 있는 것:

- `Aquarium.Fish.FacingIsContinuous` — 방향이 프레임 사이에 튀지 않는다.
- `Aquarium.Fish.BoneAnglesAreContinuous` — 본 각도가 튀지 않는다.
- `Aquarium.Fish.FacingHasNoLongTwistAcrossVertical` + `MaxSwingStepDeg`/`MaxTwistStepDeg`의
  Catch2 테스트 — 수직 전환의 비틀림 한도(M4c).
- `SwimAnimation`의 진폭·주기가 속도를 따르는 것은 규칙 계층 테스트로 고정되어 있다.
- `Aquarium.Fish.UpVectorStaysUpright` — **이 테스트는 구조상 빨간불이 될 수 없다**(M4c에서
  확인). F-13의 "바로 선 자세" 보장은 실제로는 `MaxTwistStepDeg` 쪽이 하고 있다. **그러므로
  M5는 이것과 같은 모양의 테스트를 또 만들지 않는다.**

M5가 반드시 더해야 하는 것은 셋이고, 셋 다 기존 테스트가 **한 번도 도망을 구동해 본 적이 없기
때문에** 필요하다.

1. **도망 시작 프레임의 방향 연속성** — 기존 연속성 테스트는 Wander와 방향키만으로 돌린다.
   도망은 원하는 방향을 한 프레임에 최대 180도 뒤집는, 이 게임에서 **가장 거친 방향 입력**이다.
   `FacingIsContinuousAcrossFlee`는 정면으로 오던 물고기의 코앞을 클릭하고, 프레임별 방향 변화가
   `MaxSwingStepDeg + MaxTwistStepDeg`(**리터럴이 아니라 `aquarium::FacingParams`에서 유도**)를
   넘지 않는지 본다.
2. **미끄러지지 않는다** — SRS F-13의 이 절반은 **지금 어떤 테스트도 검사하지 않는다.** 미끄러짐은
   몸이 향한 쪽과 실제로 가는 쪽이 어긋나는 것이다. `FleeDoesNotSlide`는 도망·회복 전 구간에서
   속도 벡터와 액터 전방축의 각도가 한도 안에 있는지 본다. 속도 배율을 새로 넣는 M5에서 이것이
   깨지기 가장 쉽다(가속도를 같이 올리지 않기로 한 이유이기도 하다).
3. **진폭이 상태를 따른다** — F-13은 "속도**와 상태**를 따른다"이다. 도망 중 속도가 2.2배가 되므로
   꼬리 진폭은 `SwimAnimation::Amplitude`에 따라 커져야 한다. `FleeIncreasesTailAmplitude`는 순항
   중과 도망 중의 최대 본 각도를 비교하되, **기대값을 `SwimAnimation::Amplitude`에서 유도**한다.

**만들지 않는 것**: 새 upright 테스트, 새 본 연속성 테스트, 수직 전환 테스트. 전부 M4c가 이미
고정했고 도망이 바꾸지 않는다.

## 개발 전용 플래그 문법 — 기억이 아니라 이 표를 보고 쓴다

```
-AquariumAutoClick=<토큰>[,<토큰>...]
   토큰 = <초>@<nx>x<ny>
   초  : 세션 시작(BeginPlay) 기준 경과 시간, 0보다 큰 실수
   nx  : 뷰포트 가로 비율 0.0 ~ 1.0 (0 = 왼쪽 끝)
   ny  : 뷰포트 세로 비율 0.0 ~ 1.0 (0 = 위쪽 끝)
   구분자는 '@' 와 'x' 하나씩. 공백은 트림된다. 예:
   -AquariumAutoClick="4.0@0.50x0.46,4.2@0.50x0.46,7.0@0.12x0.80,10.0@0.50x0.62"
```

`-AquariumAutoInput`과 **똑같은 실패 양식**을 쓴다 — 파서는 알아볼 수 없는 토큰에 경고만 찍고
조용히 무시한다. M4c에서 계획서가 지어낸 토큰이 전부 무효라 "입력이 하나도 없는 그럴듯한 클립"을
만들 뻔했다. 그래서:

- 경고 문자열은 두 개뿐이다: `AquariumAutoClick: bad token '...'; entry ignored`,
  `AquariumAutoClick: coords out of range in '...'; entry ignored`.
- 파싱이 끝나면 **`AquariumAutoClick: armed %d clicks`를 반드시 찍는다.**
- **캡처 하네스는 두 경고가 0건이고 `armed N`의 N이 기대한 개수와 같은지 단언한다.** 하나라도
  어긋나면 그 자리에서 실패한다.

```
-AquariumClickLog=<절대 CSV 경로>
   헤더: index,time_s,ndc_x,ndc_y,hit_plane_x,hit_fish_index,state_before
   빈 바다는 hit_fish_index = -1, hit_plane_x = 0.
   별명은 절대 쓰지 않는다. 물고기 인덱스는 실행 내 등록 순서일 뿐이다.
-AquariumNoFlee        # 클릭 처리와 도망 층을 통째로 끈다(항목별 성능 분해용)
```

## 성능 — 비용 모델과 재측정 규약

기준선은 M4c의 **평균 63.46 fps / p95 16.72 ms**(1920×1080 에디터 빌드)이고 SRS 게이트는
60 fps / 22 ms다. 여유는 약 **5.4 %**.

| 항목 | 빈도 | 예상 비용 |
|---|---|---|
| 역투영 1회 | 클릭당 | 행렬 역변환 1회. 무시 가능 |
| `PickFrontmostHit` 37회 | 클릭당 | ≈ 400 flop. 무시 가능 |
| `FleeStateMachine::Step` | 물고기당 매 틱 | 비교 2 + 뺄셈 1. 37마리 합쳐 마이크로초 이하 |
| 도망 중 무리 건너뛰기 | 도망 중인 물고기당 | **음의 비용**(보이즈를 건너뛴다) |

**즉 설계상 프레임 시간에 측정 가능한 변화가 없어야 한다.** 이것은 예측이고, M4b에서 "반투명
커튼이 비쌀 것"이라는 예측이 측정으로 반증된 전례가 있으므로 그대로 믿지 않고 잰다. 다만
**실행 간 노이즈 바닥이 약 1.3 fps이므로 1.3 fps 미만의 차이는 어느 방향이든 신호로 읽지
않는다** — 개선으로도 퇴행으로도 보고하지 않고 "노이즈 바닥 이하"라고 적는다.

**예비 레버(`GridSizeZ` 128 → 64, +17.1 fps)를 언제 쓰는가**: M5 측정에서 **평균이 60 fps 아래로
내려갔을 때만.** 그렇지 않으면 쓰지 않고 M6으로 넘긴다. 지금 미리 쓰면 M6의 쿡 빌드가 실제로 얼마나
빠른지, 그리고 그 뒤에 추가되는 비용이 얼마인지 **영구히 가려진다.** 60 fps 미달 시 순서는
(1) `GridSizeZ` 128 → 64, (2) 부유 입자 커튼 3 → 1, (3) SSAO 끄기이며 **하나 되돌릴 때마다 다시
잰다.**

## 알려진 한계 — 미리 적어 둔다

- **역투영 경로는 Automation에서 검증되지 않는다.** `-nullrhi` 자동화에는 게임 뷰포트가 없어
  `DeprojectScreenPositionToWorld`가 의미 있는 값을 주지 않는다. 그래서 Automation은 **구성한
  광선으로 `PickFrontmostHit`를 직접** 검증하고, 화면 좌표 → 광선 구간은 **실제 실행의 클릭
  로그 CSV**로 검증한다. `PropMaterialsCompile`이 `-nullrhi`에서 셰이더 컴파일을 검사하지 못하는
  것과 같은 종류의 한계이며, 같은 방식으로 1차 방어선을 실제 실행에 둔다.
- **타원 근사는 지느러미 끝을 조금 넘게 잡는다.** 바운드 기반이므로 갈라진 꼬리의 사이 빈 공간도
  적중으로 친다. 아이가 물고기를 누르려는 의도였을 때 관대한 쪽으로 틀리는 것이므로 의도적이다.
- **도망 중 분리(보이즈)도 같이 꺼진다.** 무리를 통째로 건너뛰기 때문이다. 0.8초 동안 다른 종과
  겹칠 수 있고, 겹치면 회복 시점에 풀린다. 분리만 남기는 분기를 두지 않은 이유는 `SchoolingSteer`가
  세 항을 한 벡터로 합쳐서 돌려주기 때문이고, 그것을 쪼개면 M4c가 검증해 둔 혼합비의 의미가 바뀐다.
