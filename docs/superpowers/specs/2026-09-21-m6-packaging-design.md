# M6 설계 — macOS 패키징·성능 판정·출하 검증

작성일: 2026-09-21 · 상태: 사용자 위임, 결정은 이 문서에 기록

## 왜 이것이 마지막인가

M1~M5는 **게임을 만들었다.** M6은 아무 기능도 더하지 않는다. M6이 하는 일은 딱 하나다 —
**지금까지 "됐다"고 적어 둔 것이 실제로 아이 손에 갈 물건에서도 사실인지 확인하는 것.**

그 차이는 수사가 아니다. 이 프로젝트가 지금까지 측정하고 검증한 모든 것은 **에디터 빌드**에서
나왔다. 에디터 빌드는

- 쿡되지 않은 에셋을 읽고(셰이더를 그 자리에서 컴파일하고 DDC를 쓴다),
- 에디터 전용 모듈을 전부 로드하고 있으며,
- **MCP 플러그인의 HTTP 서버를 포함한 개발 도구를 그대로 달고 있고,**
- SRS가 성능 판정 대상으로 지정한 빌드가 **아니다.**

즉 **지금 이 저장소에는 SRS 기준의 공식 성능 판정이 한 건도 없다.** 63.50 fps는 에디터 빌드의
수치이고, SRS 38행은 "패키징한 개발 빌드에서 30초 예열 후 3분"이라고 적혀 있다. M6이 그것을 처음으로
한다.

M6의 완료 조건은 "패키지가 만들어졌다"가 아니라 **"패키지가 만들어졌고, 그 패키지에 대해 SRS의 모든
항목을 판정했다"**이다.

## 지금 상태 — 가정하지 않고 확인한 것

| 항목 | 확인 방법 | 결과 |
|---|---|---|
| 규칙 계층 | `ctest` | 103개 (M5까지) |
| Unreal Automation | `Automation RunTests Aquarium` | 60개 |
| 성능 | `measure_m2b_perf.sh` | 평균 63.50 fps / p95 16.71 ms — **에디터 빌드, 65초 측정** |
| **MCP 플러그인의 출하 포함 여부** | `Aquarium.uproject` + `ModelContextProtocol.uplugin` 직접 확인 | **포함된다. 아래 참조** |
| 게임 타깃 패키징 | 한 번도 하지 않았다 | `RunUAT BuildCookRun` 미실행 |
| Shipping 구성 빌드 | 한 번도 하지 않았다 | 컴파일된 적 없음 |

### MCP 플러그인은 지금 상태로 출하된다 — 형식적 확인이 아니다

`docs/SETUP.md:97`은 "배포 게임에는 이 플러그인의 서버가 포함되지 않도록 패키징 단계에서 확인한다"고
적었다. 확인해 보니 **확인이 아니라 수정이 필요한 상태**다.

```
$ cat unreal/Aquarium/Aquarium.uproject      # Plugins: ModelContextProtocol, AllToolsets — 조건 없이 Enabled
$ python3 -c "..." ModelContextProtocol.uplugin
  module ModelContextProtocol        Runtime  Default
  module ModelContextProtocolEngine  Runtime  Default
  module ModelContextProtocolEditor  Editor   Default
```

**두 개의 Runtime 모듈이 `LoadingPhase: Default`로 있다.** `Type`이 `Editor`가 아니라 `Runtime`인
모듈은 쿡·스테이징 대상이고 게임 실행 시 로드된다. `.uproject`의 플러그인 항목에는 아무 제한도 없다.
즉 **아무 조치 없이 `BuildCookRun`을 돌리면 초등학생에게 주는 게임 안에 MCP 런타임이 들어간다.**
`AllToolsets`는 21개 툴셋 플러그인을 끌고 들어오므로 파급은 더 크다.

이것은 "확인해 보니 괜찮더라"로 끝날 항목이 아니었다. M6은 **먼저 고치고, 그 다음 그 수정이
실제로 먹혔는지를 패키지에서 단언**한다.

## 결정 사항 (아쿠부장 판단, 2026-09-21)

| 항목 | 결정 | 이유 |
|---|---|---|
| **출하 구성** | **아이에게 주는 것은 `Shipping`, SRS 성능을 재는 것은 `Development`. 둘 다 패키징한다.** | SRS 38행이 성능 측정 대상으로 **개발 빌드**를 명시하고, 자동 캡처(`-AquariumAutoClick` 등)가 가능한 이유도 개발 빌드가 `#if !UE_BUILD_SHIPPING`을 살려 두기 때문이다. 그러나 아이가 받는 빌드에 개발 플래그가 남아 있을 이유는 없다. 둘 다 만들면 **개발 플래그 배제 검사가 공허하지 않게 된다** — Shipping 바이너리에서 0건이라는 주장은 같은 검사를 Development 바이너리에 돌려 0이 아님을 보여야만 의미가 있다 |
| **MCP 플러그인 배제 방식** | `.uproject`의 두 플러그인 항목에 **`"TargetAllowList": ["Editor"]`** 를 추가한다. 플러그인을 비활성화하지 않는다 | 비활성화하면 M1~M5가 쓰던 `CaptureViewport` 검증 채널이 사라진다(`docs/SETUP.md`의 MCP 절). `TargetAllowList`는 에디터 타깃에서만 플러그인을 켜므로 개발 워크플로는 그대로이고 게임 타깃의 쿡·스테이징에서만 빠진다. **UBT 수준에서 빠지므로 "런타임에 서버를 안 켠다"가 아니라 "코드가 없다"** 가 된다 |
| **MCP 배제의 검증 방식** | **패키지 안의 파일 목록 + 실제 실행 중 포트 상태, 두 가지 모두.** 파일 검사는 `Aquarium.app` 전체에서 `ModelContextProtocol`·`Toolset` 문자열을 가진 바이너리와 `.pak`/`.ucas` 안의 해당 에셋 경로가 0건인지 본다. 포트 검사는 패키지를 실제로 60초 띄워 두고 그 사이 `lsof -nP -iTCP:8000 -sTCP:LISTEN`이 0행인지 본다 | 파일만 보면 "이름이 다른 모듈이 서버를 연다"를 못 잡고, 포트만 보면 "이번엔 안 켜졌다"밖에 말하지 못한다. **둘 중 포트 검사는 특히 공허해지기 쉽다** — 서버는 에디터에서 `ModelContextProtocol.StartServer`로 시작하므로 게임에서는 어차피 안 켜질 수 있고, 그러면 플러그인이 통째로 들어 있어도 초록불이 난다. 그래서 파일 검사가 1차, 포트 검사는 보조다 |
| **검사가 무는지 증명하는 방법** | 패키지 검증 스크립트를 **에디터 바이너리 디렉터리에 겨눠서** 돌리고 `FAIL`이 나오는 것을 확인한다 | 재패키징은 20분 이상 걸린다. 에디터 쪽에는 MCP 모듈이 **실제로 존재**하므로, 같은 검사가 거기서 빨간불이 나면 그 검사는 "찾을 줄 아는" 검사다. `PropMaterialsCompile`이 `checked 0 of 13`으로 통과한 사고의 재발 방지가 정확히 이 형태다 |
| **성능 판정 순서** | **(1) 패키지 개발 빌드를 SRS 규약(30초 예열 + 180초)으로 먼저 잰다. (2) 평균이 60 fps 이상이면 예비 레버를 쓰지 않고 그대로 판정한다. (3) 60 fps 미만일 때만 `GridSizeZ` 128 → 64를 쓰고 다시 잰다** | 레버(+17.1 fps)는 M4b·M4c·M5를 거치며 **일부러 아껴 둔 것**이고, 그 이유가 "쿡 빌드의 진짜 여유를 M6이 한 번은 봐야 한다"였다. 먼저 써 버리면 그 정보가 영구히 사라진다. 쿡 빌드는 보통 에디터보다 빠르지만 **보통이 언제나는 아니므로** 예측이 아니라 측정으로 정한다 |
| **측정 길이** | `RUN_SEC=210`, `WARMUP_SEC=30` | 기존 `measure_m2b_perf.sh`의 기본값은 `RUN_SEC=95`다. 그대로 쓰면 예열 30초를 빼고 **65초**만 남아 SRS의 "3분"에 미달한다. **공식 판정 실행은 반드시 210초여야 한다** |
| **노이즈 처리** | **실행 간 노이즈 바닥 약 1.3 fps.** 그보다 작은 차이는 개선으로도 퇴행으로도 읽지 않는다. 공식 판정은 **2회 실행의 평균**으로 한다 | M4b~M5에서 유지해 온 규약 그대로. 단 **SRS 게이트 판정 자체는 평균값으로 하되, 두 실행 중 하나라도 60 fps 아래면 그 사실을 숨기지 않고 적는다** |
| **개인정보 검증 방식** | **두 실행으로 나눈다.** (A) 자동 실행: `-AquariumAutoNickname=<고유 토큰>`으로 패키지를 돌린 뒤 로그·Saved·`~/Library` 전체에서 토큰을 grep하고, **발견된 모든 줄이 명령줄 에코 줄인지** 확인한다. (B) 수동 실행: 사용자가 패키지를 직접 띄워 별명을 손으로 입력한 세션을 돌린 뒤 같은 grep이 **0건**인지 본다 | **엔진은 명령줄 전체를 로그에 찍는다.** 그래서 개발 플래그로 별명을 넣은 실행에서 grep이 1건이라도 걸리는 것은 당연하고, "0건이어야 한다"고 적으면 그 검사는 **영원히 빨간불**이거나 검사를 약하게 고쳐 무력화된다. 반대로 A만 하면 "게임 코드가 별명을 쓴 적 있는가"를 못 가린다. 그래서 **A는 위치를 가리고, B는 진짜 경로를 판정한다.** B가 SRS 52행에 대한 유일한 정직한 답이다 |
| **개인정보 검사가 무는지 증명** | `HudWidget`/`DiverPlayerController`에 별명을 찍는 `UE_LOG` 한 줄을 **임시로** 넣고 에디터 빌드를 돌려 A 검사가 "에코 줄이 아닌 곳에서 발견"으로 빨간불이 되는지 본다. 확인 후 되돌린다 | 지금 코드에는 별명을 찍는 로그가 한 줄도 없다(`grep`으로 확인). 그러면 검사는 **아무것도 없는 것을 찾아 통과**한다 — `checked 0 of 13`과 같은 모양이다. 변이 없이는 통과에 의미가 없다 |
| **개발 플래그 배제 검증** | Shipping 패키지 바이너리에 `strings`를 돌려 `AquariumAutoClick`·`AquariumAutoInput`·`AquariumClickLog`·`AquariumFrameStats`·`AquariumAutoNickname`·`AquariumNoFlee`·`AquariumNoSchooling`·`AquariumNoPropAvoid`·`AquariumCaptureUI`·`AquariumAutoExitAfter`·`AquariumAssignmentSeed`가 **모두 0건**인지 본다. **같은 명령을 Development 패키지에 돌려 0이 아님을 함께 기록한다** | `strings`가 0을 돌려주는 이유는 두 가지다 — 정말 없거나, **검사가 엉뚱한 파일을 보고 있거나.** 후자를 배제하는 유일한 방법이 대조군이다. 토큰 목록은 기억이 아니라 `grep -o "Aquarium[A-Za-z]*" DiverPlayerController.cpp`로 **소스에서 뽑는다** |
| **에셋 출처 검증 대상** | 저장소가 아니라 **스테이징된 패키지**. 외부 에셋 5건의 원본 바이트가 저장소에서 안 바뀐 것(`git diff`)에 더해, **패키지 안에 실제로 들어간 폰트·텍스처가 그 원본에서 나온 것**임을 확인한다 | M4a~M5의 `git diff --stat` 확인은 "저장소를 안 건드렸다"까지만 말한다. 배포물에 무엇이 들어갔는지는 별개 질문이고, M6의 완료 조건에 적힌 "에셋 출처 확인"은 **배포물**에 대한 것이다 |
| **패키지의 보관 위치** | 저장소 밖. `/private/tmp/claude-501/<세션>/scratchpad/m6_package/`에 만들고 **커밋하지 않는다.** 저장소에는 **검증 산출물(로그 요약·해시 목록·성능 보고서)만** 남긴다 | `AGENTS.md`: 빌드 캐시·대형 바이너리를 커밋하지 않는다. 패키지는 수 GB이고 재현 명령이 있으므로 산출물이 아니라 중간물이다 |
| **판정 방식** | 종전과 동일 — 캡처를 눈으로 보고 직전 마일스톤과 비교한다. M6은 **새 캡처를 패키지 실행으로** 찍어 에디터 빌드 캡처와 비교한다 | 쿡은 셰이더·텍스처 압축·LOD를 바꾼다. "패키지에서도 같아 보이는가"는 헤드리스로 답할 수 없는 질문이고, 이 프로젝트에서 머티리얼이 조용히 회색으로 떨어진 전례가 두 번 있다 |

## UBT 앱 마무리 실패 — M0부터 이월된 것의 정면 처리

`docs/SETUP.md:69-74`의 상태: 게임 타깃 컴파일은 성공하고 `Binaries/Mac/Aquarium.app`도 생기는데
UBT 마지막의 **App finalization(xcodebuild PostBuildSync)** 이 `Touch UBT generated tiles` 스킴
pre-action에서 **출력 없이 exit 65**로 죽는다. 같은 `xcodebuild` 명령을 손으로 치면 `BUILD SUCCEEDED`.
샌드박스 해제, `Build/Mac/Resources` 생성, `TMPDIR` 부재 재현 전부 원인이 아니었다.

**"M5/M6 패키징 단계에서 재확인한다"고 이월했고, 지금이 그 때다.** `RunUAT BuildCookRun`은 내부에서
UBT를 불러 게임 타깃을 빌드하므로 **같은 단계를 반드시 지난다.** 우회 명령이 통하니 괜찮다고 넘기지
않는다. 이유는 셋이다.

1. **exit 65는 xcodebuild의 일반 실패 코드다.** 무엇이 실패했는지 아무것도 말해 주지 않는다. 원인을
   모르는 채 "앱은 생겼으니 괜찮다"고 하면, 서명·번들 구조·Info.plist·아이콘 중 무엇이 빠졌는지
   모르는 앱을 아이 기기에 설치하게 된다.
2. **손으로 친 명령이 성공한다는 사실 자체가 단서**다. 차이는 명령이 아니라 **환경**에 있다 —
   UBT가 자식 프로세스에 주는 환경 변수, 작업 디렉터리, 샌드박스 프로파일 중 하나다.
3. 우회를 택하더라도 **한 줄로 재현되지 않는 빌드는 이 프로젝트의 제1원칙 위반**이다. 우회조차
   스크립트에 박아야 한다.

### 진단 절차 (추측 금지, 증거만)

| 단계 | 무엇을 본다 | 왜 |
|---|---|---|
| D1 | UBT를 `-verbose`로 다시 돌려 `Engine/Programs/UnrealBuildTool/Log.txt`에서 실제 `xcodebuild` 호출 줄과 **그 앞뒤 환경 설정**을 뽑는다 | 실패가 나는 정확한 명령과 인자를 기억이 아니라 로그에서 확보한다 |
| D2 | 생성된 `.xcodeproj`/`.xcworkspace`에서 `Touch UBT generated tiles` **pre-action 스크립트 본문**을 읽는다 | pre-action 출력은 Xcode 빌드 로그에만 가고 stdout에 안 나온다. "출력 없이 실패"의 직접 설명이 여기 있을 가능성이 가장 높다 |
| D3 | 같은 `xcodebuild` 명령에 **`-resultBundlePath`** 를 붙여 손으로 돌린 뒤, 성공하든 실패하든 result bundle 안의 pre-action 로그를 연다 | 손 실행이 성공하더라도 pre-action이 **경고를 내면서** 지나갔는지 확인할 수 있다 |
| D4 | D1에서 확보한 명령을 `env -i`로 **환경을 비우고** 돌려 실패를 재현해 본다. 재현되면 변수를 하나씩 되돌려 범인을 특정한다 | "손으로는 되는데 UBT 안에서는 안 된다"의 유일하게 남은 가설이 환경 차이다 |
| D5 | D1~D4로도 원인이 안 나오면 **Xcode 26.1.1을 `/Applications/Xcode-26.1.1.app`에 병행 설치**하고 `xcode-select`로 전환해 그대로 다시 돌린다 | `docs/SETUP.md`가 M0에 이미 적어 둔 대비책이다. Epic 문서는 UE 5.8에 26.0 최소·26.1.1 권장을 적고 **27.x를 언급하지 않는다.** 즉 지금 쓰는 조합은 처음부터 지원 범위 밖이고, 이것이 사실이면 "고치는" 것이 아니라 **지원 버전으로 내려가는 것**이 정답이다 |

### `RunUAT BuildCookRun`이 같은 벽에 부딪히면 — 미리 정해 둔 답

**있다. 지원되는 경로가 실제로 있다.** 순서대로 쓴다.

1. **D5(Xcode 26.1.1)가 1순위 해결책이다.** 지원 조합으로 내려가는 것은 우회가 아니라 정상화다.
   비용은 다운로드·설치 시간뿐이고, 성공하면 SETUP.md의 M0 이월 항목이 **해소**된다.
2. **그래도 안 되면: 빌드와 쿡을 분리한다.** UBT 마무리가 실패해도 **컴파일·링크는 성공하고
   `Aquarium.app` 바이너리는 나온다**(M0에서 확인). 그러므로
   - (a) 게임 타깃을 `Build.sh`로 빌드하고,
   - (b) M0에서 성공이 증명된 `xcodebuild … UE_XCODE_BUILD_MODE=PostBuildSync` 명령을 **스크립트
     안에서** 실행해 앱을 마무리한 뒤,
   - (c) `RunUAT BuildCookRun … -skipbuild -cook -stage -pak -package`로 이어 간다.

   `-skipbuild`는 UAT의 **공식 스위치**이고, "바이너리는 이미 있다"를 뜻한다. 즉 이 경로는 임시
   해킹이 아니라 UAT가 제공하는 분리 실행이다. 다만 **(b)가 스크립트에 박혀 있어야** 재현 가능성이
   유지되고, `docs/SETUP.md`에 **알려진 편차로 명시**해야 한다.
3. **2번까지 실패하면 그때는 M6을 "패키징 불가"로 판정한다.** 성능 판정도 에셋 검증도 패키지가
   없으면 성립하지 않으므로, 억지로 만든 반쪽 번들로 수치를 내지 않는다. **근거 없이 목표를
   달성했다고 보고하지 않는다**(SRS 40행).

**하지 않을 것:** 엔진 소스나 생성된 `.xcodeproj`를 손으로 고치는 것. 다음 엔진 갱신이나 프로젝트
파일 재생성에 조용히 사라지는 수정이고, `.uasset`을 손으로 안 고친다는 원칙과 같은 이유다.

## 성능 — 무엇을 판정하고 무엇을 판정하지 않는가

SRS 36~40행이 요구하는 것을 그대로 쓴다.

| SRS 요구 | M6의 대응 |
|---|---|
| 기준 기기 M5 10코어 / 24GB | `sysctl` 출력을 보고서에 박는다(`measure_m2b_perf.sh`가 이미 한다) |
| **패키징한 개발 빌드** | `BuildCookRun -configuration=Development`로 만든 `Aquarium.app`을 직접 실행 |
| **30초 예열 후 3분** | `WARMUP_SEC=30 RUN_SEC=210` |
| 평균 60 fps, p95 22 ms | 게이트. **둘 다** 넘어야 통과 |
| 해상도·설정 기록 | 1920×1080, `-ForceRes`, 업스케일 없음, 그래픽 설정은 커밋된 `DefaultEngine.ini` 그대로 |
| 4K는 별도 품질 모드 | **범위 밖으로 명시한다.** SRS도 "별도 검증"이라고 적었다 |
| 미달 시 조정 순서 | (1) `GridSizeZ` 128 → 64, (2) 부유 입자 커튼 3 → 1, (3) SSAO 끄기. **하나 되돌릴 때마다 다시 잰다** |

**첫 측정 장면이 SRS와 다르다는 점은 숨기지 않는다.** SRS 37행은 "제어 1 + 배경 19"라고 적혀 있고
실제 장면은 **배경 36마리 + 프롭 22개**다. M2b에서 PRD의 "30~40마리" 요구를 따라 늘린 것이고,
따라서 측정은 **SRS가 적은 것보다 무거운 장면**에서 이뤄진다. 게이트를 유리하게 바꾸지 않았다는
뜻이므로 그대로 두고 보고서에 한 줄로 적는다.

### 예비 레버를 쓰는 판단은 기계적으로 한다

```
공식 실행 2회의 평균 A, p95 P
A >= 60.0 and P <= 22.0   → 통과. 레버를 쓰지 않는다. 끝.
A <  60.0 or  P >  22.0   → GridSizeZ 128 → 64 적용 → 레벨 재빌드 → 같은 규약으로 재측정
                             (그래도 미달이면 커튼 3→1, 그 다음 SSAO 순으로 하나씩)
```

**"60에 가까우니 미리 써 두자"는 하지 않는다.** 그 판단은 M4b·M4c·M5에서 세 번 유보했고 유보한
이유가 이 측정을 있는 그대로 보기 위해서였다.

## 개발 플래그 — 무엇이 어느 빌드에 남는가

지금 개발 전용 코드는 전부 `#if !UE_BUILD_SHIPPING` 안에 있다(`DiverPlayerController.cpp` 15곳,
`FishSchoolSubsystem.cpp` 1곳). 이 전처리기의 의미는 정확히 다음과 같다.

| 구성 | `UE_BUILD_SHIPPING` | 개발 플래그 |
|---|---|---|
| Editor | 0 | **있음** |
| **Development (패키지)** | 0 | **있음** ← SRS 성능 측정과 자동 캡처가 가능한 이유 |
| **Shipping (패키지)** | 1 | **없음** ← 아이가 받는 빌드 |

여기서 놓치기 쉬운 것: **개발 빌드에 플래그가 남아 있는 것은 결함이 아니라 설계다.** 결함이 되는
경우는 딱 하나 — **Shipping에도 남아 있는 경우**다. 그래서 검사는 "패키지에 플래그가 없다"가 아니라
**"Shipping 패키지에는 없고 Development 패키지에는 있다"** 를 단언한다. 앞 절 결정표의 대조군이
이것이다.

부수 효과 하나를 미리 적어 둔다. **Shipping 빌드에서는 `-AquariumAutoNickname`이 동작하지 않으므로
헤드리스 캡처가 불가능하다.** 따라서 Shipping 빌드에 대한 검증은 (1) 바이너리 문자열 검사,
(2) 실행해서 입장 화면이 뜨는지, (3) 사용자가 직접 한 세션을 노는 것 — 이 셋뿐이다. 그것이 옳다:
아이가 받을 빌드에 자동화 구멍이 없다는 것이 바로 우리가 원하는 성질이다.

## 학생 개인정보 — 마지막 확인 기회

`AGENTS.md`와 SRS 52행: 별명은 **메모리에만** 유지하고 저장·전송·로그 기록하지 않는다.

지금까지의 근거는 "그렇게 짰다"이다. 코드 확인 결과도 그와 일치한다 — 별명을 찍는 `UE_LOG`가 없고,
디스크에 쓰는 곳은 `FFileHelper::SaveStringToFile` 두 군데뿐이며 둘 다 개발 전용
(`-AquariumFrameStats`, `-AquariumClickLog`)이고 별명 열이 없다. **그러나 그것은 소스 검사이고,
`AGENTS.md`는 소스 문자열 검사로 실제 동작 테스트를 대체하지 말라고 적어 두었다.**

M6이 하는 것은 **실제 패키지를 돌린 뒤 디스크를 뒤지는 것**이다.

```
검사 대상 (패키지 실행 1회 후):
  ~/Library/Logs/Aquarium/                 게임 로그
  ~/Library/Application Support/Epic/      엔진이 쓰는 사용자 설정
  ~/Library/Preferences/                   plist
  <패키지>/Aquarium.app/                    번들 내부 (쓰기 발생 여부)
  <패키지 옆 Saved/>                        존재한다면 전부
```

두 실행의 역할은 결정표에 적은 대로다. **A(자동)는 "별명 문자열이 어디까지 번지는가"의 지도이고,
B(수동)가 판정이다.** B에서 단 한 건이라도 나오면 SRS 위반이고 M6은 통과하지 않는다.

그리고 **이 검사는 변이로 물리는 것을 먼저 증명한다.** 지금 코드에 별명 로그가 없으므로, 검사를
그냥 돌리면 "아무것도 없는 것을 못 찾고" 초록불이 난다 — `PropMaterialsCompile`의 `checked 0 of 13`과
구조적으로 같은 통과다. 임시 `UE_LOG` 한 줄을 넣어 빨간불을 본 뒤 되돌린다.

## 에셋 출처 — 저장소가 아니라 배포물에 대해

M4a~M5의 확인은 전부 `git diff --stat main...HEAD -- assets/`이었다. 그것이 답하는 질문은
**"우리가 원본을 건드렸는가"**이고, M6의 질문은 **"배포물에 무엇이 들어갔는가"**다. 다른 질문이다.

| 검사 | 방법 | 통과 기준 |
|---|---|---|
| 저장소 원본 불변 | `git diff --stat main...HEAD -- assets/models assets/textures assets/fonts` | 출력 없음 |
| 배포물의 폰트 | 스테이징된 `.pak`/`.ucas`에서 `NotoSansKR` 에셋이 **존재**하는지 | 1건 이상 (없으면 F-04가 깨지고 한글이 두부가 된다) |
| 배포물의 출처 미기재 에셋 | 스테이징 에셋 목록(`UnrealPak -list` 또는 `AssetRegistry.bin`)에서 `/Game/` 아래 항목을 뽑아 `docs/ASSETS.md` 표와 대조 | 표에 없는 **외부 유래** 에셋 0건 |
| 라이선스 문서 동봉 | `assets/fonts/OFL.txt`의 내용이 배포물에서 확인 가능한가 | OFL 1.1은 **폰트 재배포 시 라이선스 사본 동반**을 요구한다. 게임 번들에 넣거나 README에 명시한다 |

**OFL 항목은 M6에서 처음 걸리는 실질적 의무다.** `docs/ASSETS.md`는 "OFL: 폰트 단독 판매 금지,
임베드·재배포 허용"이라고 적었고 그것은 맞지만, OFL 1.1은 사본 동반도 요구한다. 지금 패키지에는
아무것도 안 들어간다. M6이 이것을 닫는다.

## 사용자 수동 확인 — 헤드리스가 끝나는 자리

## 알려진 한계 — 미리 적어 둔다

- **Shipping 빌드는 자동으로 검증할 수 없다.** 개발 플래그가 없으므로 자동 캡처도 자동 입장도 못
  한다. 검증은 바이너리 문자열 검사와 사용자의 손에 달려 있다. 이것은 결함이 아니라 의도한
  성질이지만, **"Shipping 빌드의 게임 플레이는 사람만 확인했다"** 가 M6의 사실이다.
- **`TargetAllowList`가 의존 플러그인까지 막는지는 측정으로 확인한다.** `AllToolsets`는 21개
  플러그인을 끌고 오고, 의존 플러그인은 부모가 꺼져도 다른 경로로 켜질 수 있다. 그래서 검증이
  "설정했다"가 아니라 **"패키지 안에 없다"** 여야 한다.
- **포트 검사는 약한 검사다.** 위 결정표에 적은 대로 파일 검사가 1차다. 포트 검사만 초록불인 상태를
  통과로 읽지 않는다.
- **에디터 빌드와 패키지 빌드의 성능은 직접 비교할 수 없다.** 쿡·셰이더·텍스처 스트리밍 설정이 모두
  다르다. M6 보고서는 63.50 fps를 **기준선이 아니라 참고**로 적는다. SRS 게이트는 패키지 수치만으로
  판정한다.
- **4K 품질 모드는 범위 밖이다.** SRS가 별도 검증이라고 적었고 M6에서 하지 않는다.
